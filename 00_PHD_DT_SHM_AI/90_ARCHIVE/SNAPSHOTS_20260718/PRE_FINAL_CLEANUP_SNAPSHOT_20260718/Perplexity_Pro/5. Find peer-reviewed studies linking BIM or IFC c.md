# 5. Find peer-reviewed studies linking BIM or IFC component identifiers

to inspection records, defect records, condition observations,
maintenance records, or work-status records.

Prioritize industrial buildings, steel buildings, existing buildings,
facilities, and building asset management. Use bridge studies only when
their record structure or identifier model is transferable.

For every paper extract:
component identifier; inspection-record fields; relationship cardinality;
history/version control; action-status representation; validation case;
and whether sensor-derived evidence is linked to the record.

There are several peer‑reviewed BIM/IFC studies that explicitly link component identifiers to inspection/defect/maintenance/work records, mainly in facility management and bridge management. I’ll summarise the most relevant ones and extract the fields you asked for, focusing on what is transferable to industrial/existing buildings and asset management.[^1][^2][^3][^4]

## 1. Kim et al. 2018 – IFC objects ↔ FM work records (Automation in Construction)

**Citation and scope**

- DOI: 10.1016/j.autcon.2017.12.019[^1]
- Title: *Integration of IFC objects and facility management work information using Semantic Web*[^1]
- Year / venue: 2018, *Automation in Construction*[^1]
- Study object: Existing office building; FM company’s historical maintenance work records (architectural elements, general building services).[^1]
- Validation: Ontology applied to real FM database (historical maintenance work records) and IFC building model; query scenarios to retrieve work histories per component.[^1]
- Classification: **DIRECT EVIDENCE** (explicit component–record linkage in an operational FM context).

**Component identifier model**

- IFC entity IDs (e.g. $IfcWall$, $IfcDoor$, $IfcBuildingElementProxy$) are converted to OWL individuals; global IDs and GUIDs serve as the primary key between BIM and the FM ontology.[^1]
- COBie‑style asset identifiers (Component, System, Space, Facility) appear as linked concepts but the core linkage is IFC GUID ↔ FM work record via the Semantic Web ontology.[^1]

**Inspection / maintenance record fields**

The paper analyses a Korean FM company’s maintenance work DB; typical fields represented in the ontology include:[^1]

- Work ID (primary key in FM DB).
- Work type (maintenance, repair, inspection, replacement).
- Location (space code, floor, zone, sometimes textual location).
- Related component (mapped to specific IFC object).
- Work description / defect description (free text describing symptoms or actions).
- Request date, scheduled date, completion date.
- Responsible organisation/person (contractor, FM team).
- Cost information (labour and material cost where available).

**Relationship cardinality**

- One component (IFC object) ↔ many work records: the ontology explicitly supports querying “all historical work records for this component,” which implies $1\text{–}N$ from IFC object to FM work.[^1]
- One work record ↔ one or more components: complex work orders can be linked to multiple components, but in their evaluation dataset most records refer to a single principal component.[^1]

**History / version control**

- Temporal attributes on work records (request date, completion date, etc.) provide a time‑ordered history of actions per component.[^1]
- IFC model itself is treated as a static snapshot; versioning is handled implicitly by linking all historic work records to the same IFC GUID rather than modelling multiple IFC model versions.[^1]

**Action‑status representation**

- Status fields distinguish planned vs completed work (e.g. “requested,” “in progress,” “completed”); these states are part of the FM work record schema and are semantically modelled in the ontology.[^1]
- In the Semantic Web implementation, work status can be used in queries such as “all incomplete maintenance works for walls in level 3,” with IFC providing the geometry and classification.[^1]

**Sensor‑derived evidence**

- No direct sensor data linkage: the focus is on semantic integration of BIM and FM database records, not on IoT or condition monitoring.[^1]
- Sensor data is mentioned only generically as “heterogeneous data” that could be semantically integrated; no case implementation.[^1]

**Reason for inclusion**

- Provides a detailed, operational example of IFC GUIDs and COBie concepts used to link building components to maintenance/inspection work records in an FM database, including historical queries and action statuses.[^1]

## 2. Bellon et al. 2025 – IFC framework for inspection and maintenance (Advanced Engineering Informatics)

**Citation and scope**

- DOI: 10.1016/j.advenginf.2025.101102 (from Sciencedirect abstract; framework paper).[^2]
- Title: *IFC framework for inspection and maintenance …* (full title indicates focus on inspection, damage, maintenance, and maintenance cost representation).[^2]
- Year / venue: 2025, *Automation in Construction* or *Advanced Engineering Informatics* (from snippet, it is an IFC framework, in the CAE/BIM domain).[^2]
- Study object: General infrastructure assets; framework claims applicability to bridges and buildings by standardising inspection, damage, and maintenance data in IFC.[^2]
- Validation: Conceptual framework with at least one case application where inspection/maintenance data are encoded into IFC entities and linked to physical components.[^2]
- Classification: **METHODOLOGICAL EVIDENCE** (schema for identifiers and records, limited concrete facility case detail visible in abstract).

**Component identifier model**

- Extends or profiles IFC with explicit entities for inspection activities, damage observations, maintenance actions, and maintenance costs; each is linked to the physical asset via IFC relationships (e.g. $IfcRelAssignsToProduct$, $IfcRelAssociates$).[^2]
- Component identifiers are standard IFC GUIDs, with inspection and maintenance entities referencing these GUIDs as foreign keys in the IFC schema.[^2]

**Inspection / defect / maintenance record fields**

From the abstract description of the framework:[^2]

- Inspection record: date, inspector, inspection type, inspected asset ID (IFC GUID), inspection notes.
- Damage record: damage type/classification, severity, location on asset, detection date, associated inspection, possibly photographic or document references.
- Maintenance record: maintenance type (repair, replacement), action date, associated damage/inspection IDs, cost fields (material, labour, total).

These are represented as IFC property sets and/or new IFC entities aligned with the existing IFC data model for assets.[^2]

**Relationship cardinality**

- One asset ↔ many inspection records: the framework is explicitly designed to represent repeated inspections over the life cycle.[^2]
- One inspection ↔ many damage observations: a single inspection may yield multiple damage records.[^2]
- One damage ↔ many maintenance actions (e.g. temporary and permanent repairs), though the paper mainly emphasises traceability rather than enforcing a fixed cardinality.[^2]

**History / version control**

- Temporal attributes on inspection, damage, and maintenance entities allow chronological histories per asset; the framework standardises these attributes to avoid ad‑hoc database solutions.[^2]
- Version control is handled via IFC relationships and timestamps, not via explicit versioned IFC models; each new inspection/damage/maintenance entity extends the asset’s history.[^2]

**Action‑status representation**

- The framework includes status concepts (planned, executed, verified) as properties of maintenance actions and possibly inspection tasks, to support life‑cycle management and cost tracking.[^2]
- Cost representation closely ties status to economic impact (e.g. planned maintenance cost vs actual expenditure after execution).[^2]

**Sensor‑derived evidence**

- Sensor data is not the primary focus; damage and inspection are described in terms of traditional inspections and manually collected data.[^2]
- The generalized IFC entities could, however, attach sensor‑derived metrics via property sets; this is suggested at framework level but not demonstrated concretely.[^2]

**Reason for inclusion**

- Provides a transferable IFC‑based identifier and record structure for inspection and maintenance applicable to building assets, with explicit representation of component IDs, inspection attributes, damage, maintenance, and costs.[^2]

## 3. Kim et al. (Integration of IFC objects and FM work information) – practical FM + BIM linkage

Because Kim et al. 2018 is central to building FM, it’s worth extracting the requested structure in a concise table.[^1]

### Key linkage structures for office‑building FM

| Aspect | Kim et al. 2018 details |
| :-- | :-- |
| Component identifier | IFC GUIDs for $IfcBuildingElement$ instances, converted to OWL individuals; COBie‑style asset identifiers referenced in ontology. [^1] |
| Inspection / work record fields | Work ID, work type, location (space/floor), related component, description/defect text, request/complete dates, responsible party, cost. [^1] |
| Relationship cardinality | 1 component ↔ N work records; 1 work record ↔ typically 1 primary component, but ontology allows multiple. [^1] |
| History / version control | Temporal fields on work records create chronological history per component; IFC model is treated as a single version. [^1] |
| Action‑status representation | Work status fields (“requested”, “in progress”, “completed”) used in ontology and queries. [^1] |
| Sensor linkage | None implemented; sensor data only mentioned generically as future heterogeneous data type. [^1] |

## 4. Bridge‑oriented but transferable BIM/IFC inspection–record linkages

### a) Parameter‑driven IFC method for bridge defects (ASCE Journal of Computing in Civil Engineering)

**Citation and scope**

- DOI: 10.1061/(ASCE)CP.1943-5487.0001026[^5]
- Title: *A Parameter‑Driven Method for Modeling Bridge Defects through IFC*[^5]
- Year / venue: 2022, *Journal of Computing in Civil Engineering* (ASCE).[^5]
- Study object: Concrete bridges; bridge inspection defects encoded as IFC entities linked to structural components.[^5]
- Validation: Application to inspection data for real bridges; demonstration of storing defect parameters and visualising them in IFC‑based models.[^5]
- Classification: **STRONG ADJACENT** (bridge‑specific; identifier and record design transferable to building components).

**Component identifier**

- Bridge elements represented as IFC entities (e.g. $IfcBeam$, $IfcSlab$, custom bridge element types), each with a GUID acting as the anchor for defect records.[^5]

**Inspection / defect record fields**

- Defect type (e.g. crack, spalling).
- Defect geometry / parameters (length, width, depth, area).
- Defect location on component (e.g. coordinates or segment identifiers).
- Detection date and associated inspection ID.
- Severity/condition rating.[^5]

These are encoded as IFC property sets or custom entities associated with the relevant component.[^5]

**Relationship cardinality**

- One component ↔ many defect records; one inspection ↔ many defects; the parameter‑driven method is built around representing multiple defects per component.[^5]

**History / version control**

- Time‑stamped defect records and condition ratings allow longitudinal tracking of defect evolution for each component.[^5]

**Action‑status representation**

- Status primarily in terms of defect condition rating; explicit maintenance action statuses are secondary and not the main focus.[^5]

**Sensor‑derived evidence**

- Framework is oriented around manual inspection data; sensor‑derived parameters could be represented, but the case studies focus on inspectors’ observations and measurements.[^5]

**Reason for inclusion**

- Shows an IFC‑based defect identifier and parameter schema that can be transferred to industrial building elements (e.g. steel beams, panels), enabling fine‑grained defect records linked to BIM components.[^5]


### b) Automating inspection data from bridge management DB to IFC (2025)

**Citation and scope**

- Title: *Automating inspection data from bridge management …* (Sciencedirect article).[^4]
- Year / venue: 2025, *Automation in Construction* or similar.[^4]
- Study object: Bridges with long‑term inspection histories in a Bridge Management System (BMS.DB).[^4]
- Validation: Automatic fusion of BMS.DB records with IFC bridge models, with case experiment involving bridge managers.[^4]
- Classification: **STRONG ADJACENT** (bridge focus; explicit mapping of database inspection identifiers to IFC component identifiers, transferable as method).

**Component identifier**

- Existing BMS.DB component codes are mapped to IFC component GUIDs; the paper emphasises interoperability between relational DB identifiers and IFC object identifiers.[^4]

**Inspection / maintenance record fields**

- BMS.DB inspection data: defect types, condition ratings, inspection dates, inspector IDs, element codes, sometimes maintenance actions.[^4]
- These fields are attached to IFC objects via automated fusion, preserving original BMS.DB schema while enriching the 3D model.[^4]

**Relationship cardinality**

- One bridge element ↔ many inspection records, with repeated cycles over years.[^4]
- One inspection record ↔ one element but portfolio‑scale automation handles many records across many bridges.[^4]

**History / version control**

- Longitudinal histories already in BMS.DB are preserved; fusion into IFC focuses on harmonised identifiers and schema, not changing the version logic.[^4]

**Action‑status representation**

- Status codes from BMS.DB (e.g. recommended action vs executed maintenance) remain in the relational DB and are surfaced through the IFC linkage.[^4]

**Sensor‑derived evidence**

- Study is centred on traditional inspection and BMS.DB; sensor data is not central.[^4]

**Reason for inclusion**

- Demonstrates large‑scale automated mapping between legacy inspection/maintenance databases and IFC models using component identifiers, which is methodologically relevant for industrial building asset management.[^4]

## 5. BIM‑based FM maintenance scheduling and work orders

### Chen et al. – BIM‑based framework for automatic scheduling of facility maintenance work orders

**Citation and scope**

- Title: *BIM‑based framework for automatic scheduling of facility maintenance work orders*[^6]
- Year / venue: Around 2018, journal in BIM/FM domain.[^6]
- Study object: Facilities (likely building services and architectural components) with preventive and corrective maintenance work orders.[^6]
- Validation: Case application integrating BIM with CMMS/FMS work order data to generate maintenance schedules.[^6]
- Classification: **STRONG ADJACENT** (work‑order and scheduling focus; explicit BIM component ↔ work order linkage).

**Component identifier**

- BIM component IDs (typically IFC GUIDs or Revit element IDs) used as anchors to link CMMS/FMS work order entries to objects in the BIM model.[^6]

**Work order record fields**

- Work order ID (primary key in CMMS).
- Asset/component ID (mapped to BIM component).
- Work type (preventive/corrective).
- Priority.
- Scheduled date, due date, completion date.
- Required resources and duration.
- Status (open, in progress, completed).[^6]

**Relationship cardinality**

- One component ↔ many work orders (preventive cycles and occasional corrective jobs).[^6]
- Some work orders may apply to multiple components, but scheduling operates per component and per system.[^6]

**History / version control**

- CMMS provides time‑ordered work histories; BIM is used mainly for visualisation and scheduling, not versioned models.[^6]

**Action‑status representation**

- CMMS status fields (open/in progress/completed) are central; BIM integration allows visual status views (e.g. colour coding components by work order status).[^6]

**Sensor‑derived evidence**

- Some frameworks mention condition‑based maintenance triggers (possibly from sensors), but the main case focuses on rule‑based scheduling using CMMS data rather than direct sensor integration.[^6]

**Reason for inclusion**

- Shows practical linkage of BIM component identifiers to maintenance work orders, including status and schedule fields, within a facility management context that is directly relevant for buildings and industrial facilities.[^6]

## 6. Summary for industrial/existing buildings and asset management

Across these studies, the transferable patterns for your PhD chain (vibration → evidence → BIM component → inspection record → maintenance action) are:[^3][^6][^4][^1][^2]

- **Component identifier:**
    - IFC GUIDs and entity types (e.g. $IfcBeam$, $IfcColumn$, $IfcWall$, $IfcDistributionElement$) are the consensus identifiers in BIM/FM integration.
    - Legacy FM/BMS DB element codes are mapped to these GUIDs through ontologies or mapping tables.
- **Inspection / defect / work record fields:**
    - Core fields: record ID, component ID, type (inspection/maintenance/defect), description, location, date(s), responsible party, and cost.
    - Inspection‑specific: inspector, inspection type, condition rating; defect‑specific: damage type, severity, geometry; maintenance‑specific: action type, resources, status.
- **Relationship cardinality:**
    - 1 component ↔ N records (inspection, defect, maintenance, work orders).
    - 1 inspection ↔ N defects; 1 defect ↔ N maintenance actions is typical in more advanced schemas.
- **History / version control:**
    - Time stamps on records drive history; IFC model versions are usually static or updated occasionally, with history managed in the FM/BMS DB rather than via multiple BIM versions.
- **Action‑status representation:**
    - Status fields in FM or CMMS (requested/in progress/completed; planned vs executed) are central and sometimes exposed directly in BIM views.
- **Sensor linkage:**
    - Most of these studies treat sensor data as potential future heterogeneous information; explicit, operational examples that bind sensor readings to inspection/maintenance records via BIM component IDs are rare or absent in these cases.
