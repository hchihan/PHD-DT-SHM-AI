## Framing the Question

This report examines whether IFC GlobalId (GUID), BIM authoring-tool GUIDs, or facility Asset_ID codes can function as stable anchors for chaining Sensor_ID → BIM component → condition evidence → inspection record → maintenance/inspection action. The evidence base spans official buildingSMART technical documentation, peer-reviewed IFC/BIM-FM literature, and vendor/practitioner technical notes. Findings are explicitly separated into (a) normative/official statements, (b) empirical or peer-reviewed findings, and (c) practitioner/anecdotal reports, because these carry different evidentiary weight.

## Assessment: How Has IFC GlobalId Actually Been Used?

Across the reviewed literature, IFC GlobalId is used in two structurally different ways. In model-server and single-authoring-tool contexts, buildingSMART's IFC4.3 revision-control concept ties GUID plus a change-action flag to enable incremental merge logic, which is the closest official mechanism to a genuine "identity across revisions" model. In practice-oriented sensor/BIM integration studies, however, the more common pattern is *not* to trust GUID alone: the Brookes digital-twin technologies review reports that studies extending IfcSensor entities used a separate "IfcObject matching table" to link BIM GUID to BMS/sensor item IDs rather than assuming the GUID itself would remain a durable join key. Similarly, the UCL anomaly-detection framework proposes new IFC entity extensions (IfcMaintenanceHistory, IfcInspectionHistory, IfcSpareRecord) explicitly because the base schema lacks native constructs linking sensors, maintenance, and inspection activity to assets. This pattern — building an auxiliary crosswalk or schema extension rather than relying on GlobalId in isolation — recurs across the literature.[^13][^11][^2]

## Is IFC GlobalId Stable? Cross-Validated Findings

buildingSMART's own schema documentation is explicit that GlobalId "has to be persistent," but simultaneously warns that *other* serialization identifiers are not guaranteed stable between revisions or across applications — implying persistence is a design intent for GlobalId specifically, not a system-wide guarantee for all identifiers in an IFC file. Independent evidence, however, shows this intent is frequently violated in practice:[^1]

- **Authoring-tool round trips**: Revit's IFC exporter reliably reproduces GUIDs for entities with a clean 1:1 element mapping (doors, walls, standard cases) across repeated export sessions, but GUIDs for relationship and type entities (IfcRelSpaceBoundary, IfcPropertySet, IfcTypeObject) are explicitly *not* guaranteed consistent between exports, according to Autodesk's own API engineering explanation.[^4]
- **Model federation**: Multiple independent sources — an Autodesk community forum thread (2025), a buildingSMART forum thread (2020), and Autodesk support documentation — confirm that GUIDs of elements in linked/federated models are regenerated when a federated assembly is re-exported, and that duplicate GUIDs commonly appear when the same element is represented in both host and linked files.[^5][^7][^6]
- **Model splitting/merging and copy operations**: A commercial IFC-tooling vendor (simplebim) and an independent GUID-repair tool documentation both catalog specific authoring-tool operations that generate duplicate GlobalIds, including Revit's "Copy/Monitor" and "Duplicate Types" commands, ArchiCAD hotlink modules and copy-paste between projects, and Tekla model splitting/merging. This is corroborated by the open-source ifcopenshell "RegenerateGlobalIds" patch, which exists specifically because "some proprietary BIM software" generates invalid, duplicate, or non-compliant GlobalIds.[^15][^16][^8]
- **Object replacement**: No source directly measures GUID behavior under object replacement (e.g., swapping a sensor-bearing valve for a new model) as a controlled experiment; this remains an evidentiary gap (see "Unsupported Claims" below).
- **Bespoke exporters**: A CAD tool vendor (12d Model) documentation shows that some authoring tools generate an entirely new GUID on every export by default, requiring a manual "store as attribute" workaround to achieve any persistence at all — demonstrating GUID stability is fundamentally an authoring-tool implementation choice, not a schema guarantee.[^17]

Academic corroboration comes from a graph-based IFC model-merging study, which explicitly designs its comparison algorithm to *drop* GUID-based matching when cross-software export is detected, falling back to structural graph matching instead — a peer-reviewed acknowledgment that GUID reliability cannot be assumed once multiple authoring tools are involved.[^10]

## Under What Operations May GlobalId Change?

Synthesizing the sources above, GlobalId is empirically reported to change or duplicate under: (1) federation of linked/host models upon re-export; (2) copy/monitor or duplicate-type operations within a single authoring tool; (3) hotlink or module-based reuse in ArchiCAD; (4) model splitting and remerging in Tekla-based workflows; (5) export from tools without a "preserve GUID" setting enabled by default; and (6) internal GUID-generation cache bugs affecting relationship/type entities even within a single software session. buildingSMART's IFC4.3 revision-control concept is the only official mechanism addressing *intended* change (add/modify/delete) rather than incidental instability.[^6][^16][^2][^4][^5][^17]

## How Do Prior Studies Manage Changed, Duplicate, or Orphaned IDs?

Handling strategies observed across sources cluster into four approaches. First, tooling-based detection and repair: both a commercial (simplebim) and open-source (ifcopenshell/ifcpatch) tool exist specifically to scan for and regenerate duplicate or invalid GlobalIds, treating this as a routine data-quality remediation step rather than an exceptional event. Second, guideline-based prevention: Singapore's CORENET IFC-SG modelling practices instruct practitioners to check GUID consistency *before* federating and exporting models, shifting the burden to process discipline rather than technical guarantee. Third, algorithmic fallback: the graph-based merge study abandons GUID matching altogether when cross-tool export is detected, using topological graph structure as the authoritative correspondence mechanism instead. Fourth, external crosswalk tables: the Brookes review of digital twin technologies reports that BIM-IoT integration studies commonly build a separate "matching table" linking BIM GUID to BMS/sensor system item IDs, functionally decoupling sensor identity persistence from raw GUID persistence. No source in this review reports a peer-reviewed, empirically validated method for automatically detecting *orphaned* sensor-to-component mappings after a GUID change — this remains an open gap.[^9][^8][^13][^10][^15]

## Are Asset_ID–to–GlobalId Crosswalks Commonly Used?

Yes, but the evidence base is stronger for their necessity than for their standardized implementation. The IfcObject matching table reported in reviewed BIM-IoT integration studies is functionally a GUID-to-sensor-ID crosswalk. The practitioner white paper on RTU equipment identification goes furthest in formalizing this: it explicitly recommends treating a human-readable canonical Asset Tag (not the raw IFC-GUID) as the master identifier, storing it in Pset_AssetIdentification.AssetIdentifier, and propagating it unchanged into COBie, Brick, and Haystack representations — explicitly because relying on GUID alone risks "duplicates and orphaned records" when equipment is relocated or renumbered. This is a converging signal across both academic and practitioner sources: the crosswalk is not merely common, it is treated as a *necessary compensating control* for GUID's known instability, though it is documented mostly in grey literature and practitioner guidance rather than in a peer-reviewed empirical validation study.[^14][^13]

## Required Governance and Versioning Fields

Drawing on buildingSMART's IFC4.3 revision-control concept and the practitioner change-control rule for canonical asset tokens, sensor-to-component assignment records should minimally capture: an assignment effective-date and expiry/superseded-date; the specific GUID value(s) and IFC file/version hash at time of assignment (not just the current GUID); an assignment status field (active, superseded, orphaned, unverified); an approving/reviewing party and review date; a source-of-authority field identifying which system (BIM model vs. CMMS vs. sensor registry) is authoritative for the mapping; and a change-reason code recording why a reassignment occurred (object replacement, GUID regeneration, model federation, relocation). None of these fields are mandated by the IFC schema itself; they represent governance practice inferred from the convergence of buildingSMART's revision-control concept and practitioner change-control documentation, not a ratified standard.[^2][^9][^14]

## Defensible Statement on GlobalId as a Traceability Anchor

IFC GlobalId can function as a *provisionally reliable* short-term anchor within a single authoring-tool session and for geometrically well-defined, 1:1-mapped entities (doors, walls, discrete equipment items), consistent with both buildingSMART's stated design intent and Autodesk's engineering explanation of GUID generation. It is not defensible, however, as a long-term or cross-context traceability anchor without a compensating mechanism, because multiple independent sources — spanning official forums, vendor support documentation, and peer-reviewed algorithm design — confirm that GUIDs are altered or duplicated under federation, authoring-tool round trips, and copy/merge operations. The IFC4.3 revision-control concept demonstrates that buildingSMART has designed a mechanism for *intentional* change tracking, but this mechanism is not the default behavior of common authoring-tool export workflows and is not evidenced as broadly deployed. Consequently, GlobalId should be treated as one input to a traceability chain, always paired with a version-controlled crosswalk to a persistent Asset_ID, rather than as a sufficient standalone key.[^7][^16][^1][^10][^4][^6][^2]

## Risks Related to Model Revision and Object Replacement

- GUID regeneration on federated re-export can silently sever the Sensor_ID-to-component link without any explicit deletion signal, since the old GUID simply stops appearing in the new export.[^6]
- Duplicate GUIDs across discipline models (structural, MEP, architectural) can cause a sensor mapping to resolve to the wrong physical component when multiple objects share an identifier.[^7]
- Object replacement (e.g., swapping a monitored valve or a piece of mechanical equipment) has no documented, tested IFC mechanism for signaling "this new GUID is the successor to that old GUID" — this transition is currently unaddressed in the reviewed literature, constituting a genuine risk of orphaned inspection/maintenance history.
- Authoring-tool default settings (e.g., "generate new values" export mode) can regenerate GUIDs for an entire model on every re-export unless explicitly configured otherwise, creating risk of mass-orphaning of sensor mappings after routine model updates.[^18][^17]
- Relationship and type entities (property sets, space boundaries) are the least stable GUID category, so any condition-evidence or inspection-record link that depends on these entity types is at elevated risk compared to links to geometric elements.[^4]

## Minimum Governance Rules (G2)

1. Every sensor-to-component assignment record must store the GUID *and* the source IFC file identity/version/export-timestamp at the time of assignment, not merely the current live GUID.
2. A persistent, human-governed Asset_ID (independent of any authoring-tool-generated identifier) must be the primary key for the crosswalk table; GlobalId is a secondary, re-verifiable attribute.[^14]
3. Any model re-export, federation event, or authoring-tool round trip must trigger a mandatory GUID-diff/duplicate-check step before sensor mappings are considered valid for the new revision.[^15][^9]
4. Object replacement events must be logged with an explicit successor-GUID linkage and a review/approval step, since no automated schema mechanism currently performs this linkage.[^2]
5. Sensor-to-component mappings must carry an effective-date, expiry/superseded status, and reviewing-party field, consistent with the revision-control pattern buildingSMART defines for model-server change actions.[^2]
6. Periodic reconciliation (not solely event-triggered) should re-validate that live GUIDs in the current model still resolve to the Asset_IDs on record, given documented cases of silent GUID drift.[^16][^6]

## Proposed Controlled Test Using Two IFC Model Versions

A defensible empirical test would export the same building model twice from the same authoring tool under three controlled conditions: (a) no change to the model, re-export only; (b) a minor geometric edit to an unrelated element; (c) federation of the model with a second discipline model, followed by re-export. For each condition, every IfcRoot-derived entity's GlobalId would be diffed between Version 1 and Version 2, stratified by entity type (geometric element vs. relationship vs. property set vs. type object), and the percentage of GUIDs that changed, duplicated, or were dropped would be recorded. Sensor_ID-to-GUID mappings established against Version 1 would then be re-resolved against Version 2 to measure orphan rate directly. This design directly operationalizes the instability patterns reported anecdotally in vendor/forum sources  into a quantifiable, repeatable metric — something the current literature notably lacks.[^16][^4][^6]

## Claims That Remain Unsupported

Evidence is currently insufficient to support any of the following: a quantified failure rate (percentage) for GlobalId persistence across authoring tools or federation scenarios in a controlled, peer-reviewed experiment; a validated, standardized mechanism for signaling object-replacement successor relationships within the ratified IFC schema; peer-reviewed empirical validation (as opposed to conceptual proposal) of the IfcMaintenanceHistory/IfcInspectionHistory/IfcSpareRecord extensions for sensor-to-maintenance traceability; and any industry-wide consensus standard for crosswalk-table schema, versioning fields, or approval workflow for sensor-to-component assignments — the governance fields proposed in this report are inferred from convergent but non-standardized sources, not drawn from a single ratified specification.[^11]
