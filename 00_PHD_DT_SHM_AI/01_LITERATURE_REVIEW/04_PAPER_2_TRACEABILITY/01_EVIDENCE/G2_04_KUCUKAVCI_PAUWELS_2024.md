# G2_04 -- Kücükavci, Seidenschnur, Pauwels, Rasmussen & Hviid (2024)

**Efficient Management and Compliance Check of HVAC Information in the Building Design Phase Using Semantic Web Technologies.** Semantic Web, 15(5), 1959-1989. DOI: 10.3233/SW-243595. Zotero key: 8MCF7A8G.

**Source read:** Full text, complete (`G2_8MCF7A8G_PauwelsHVAC.txt`, 24 pages: Introduction, Related Work, Flow Properties Ontology, HVAC rule model, Demonstration Environment, Discussion/Limitations/Implications, Conclusions).

**Q1 -- Research problem.** BIM models frequently lack sufficient building elements or metadata for HVAC (Heating, Ventilation, Air Conditioning) design and compliance checking; existing lightweight ontologies (notably the Flow Systems Ontology, FSO) do not represent HVAC components' capacity- and size-related properties, and no prior SHACL-based rule model exists specifically for the HVAC domain. The paper extends FSO, proposes a new Flow Properties Ontology (FPO), develops a 36-shape/122-constraint SHACL rule model for HVAC compliance checking, and demonstrates it on a real building.

**Q2 -- Information architecture.** PARTIAL. Chain is: FSO/FPO ontology representation of HVAC systems/components/ports/properties -> real building's RDF data graph (converted from BIM/IFC-derived data) -> SHACL shape graph (36 shapes/122 constraints) -> validation report (pass/fail per constraint) -> (separately) SPARQL-based hydraulic capacity calculations displayed in a web interface. No sensor/inspection-evidence or human-record layer; the "record" is the validation/calculation report itself.

**Q3 -- Identity representation.** NOT_REPORTED at the `IfcRoot.GlobalId` level specifically; components are identified as RDF individuals within the FSO/FPO ontology (e.g. `fso:Pump inst:0fc738e3-3eb1-4344-b913-b3883e4083b0-0033212a`), using instance URIs that functionally resemble GUID-derived identifiers but are not explicitly discussed as IFC GlobalId-anchored identity.

**Q4 -- Identity persistence across model revisions.** NOT_REPORTED. Single-snapshot validation of one real building's data graph; no multi-revision scenario discussed.

**Q5a-e -- Provenance types.** NOT_REPORTED for all five. The paper's scope is component/property representation and rule-based compliance checking, not provenance of sensor readings, processing steps, or human actors -- and no review/approval concept appears.

**Q6 -- Model/version context.** NOT_REPORTED.

**Q7 -- Validity/applicability scope.** YES, explicit and quantified. CLAIM: the HVAC rule model (36 shapes, 122 constraints) was applied to "Frederiksberg Skole," a real building represented with 369,054 RDF triples. EVIDENCE: Conclusions section states the rule execution was performed twice, with 372 constraint violations found on the first run and 14 on the second (after corrections). Rule execution took 3.1 seconds; downstream SPARQL-based hydraulic-capacity calculation took 87 seconds (attributed partly to `FILTER NOT EXISTS` query inefficiency, discussed as a named limitation).

**Q8 -- Forward and reverse traceability.** PARTIAL. The rule model identifies which specific components/properties violate constraints (traceable from violation back to the offending RDF individual), and downstream SPARQL queries trace component-to-system membership and port-to-port flow connectivity (`fso:suppliesFluidTo`, inferred `feedsFluidTo`), but no cross-system record traceability is addressed.

**Q9 -- Validation method.** YES -- this is the paper's core, most rigorous contribution in the entire targeted corpus for quantified SHACL validation. A 36-shape/122-constraint HVAC-specific SHACL rule model, using only hard constraints, was executed against a real 369,054-triple building dataset, with two full validation-correction cycles reported and exact violation counts (372 -> 14) and runtimes (3.1s validation; 87s capacity calculation) given.

**Q10 -- Deliberate invalid-case testing.** PARTIAL/YES. CLAIM: constraint examples explicitly test for missing or malformed cardinality (e.g. `fsosh:Pipe` requiring exactly 2 `fso:Port` values via `sh:minCount 2; sh:maxCount 2`, with the message "A pipe must have exactly two flow ports"), and SPARQL-based constraints detect derived-value violations (e.g. `fsosh:AirTerminalCapacityCheck` flags when capacity is below demand or oversized by >10%; `fsosh:PipePressureDrop` flags pressure drop exceeding 100 Pa/m). EVIDENCE: Listings 1-3 give exact SHACL/SPARQL code for these constraints; the real-building run found 372 violations on first execution. LIMITATION: these are cardinality/value-range/derived-calculation violations (missing port, wrong count, out-of-range value), not specifically the identity-integrity sub-taxonomy in Paper 2's Q10 (duplicate/stale/wrong-model-revision GUID, orphan cross-system reference, broken URI to an external record). IMPLICATION: this is the strongest evidence in the corpus that a domain-specific SHACL rule model can be built, deployed, and quantitatively validated on a large real building dataset with genuine (not toy) violation detection -- but it validates *intra-model* structural/value completeness, not *cross-system, cross-record* referential integrity of the kind Paper 2's core chain requires.

**Q11 -- G3 record fields.** NOT_APPLICABLE -- no inspection-record content.

**Q12 -- ALREADY_ESTABLISHED vs REMAINING_GAP.** ALREADY_ESTABLISHED: a real, large-scale (369,054-triple), quantitatively validated domain-specific SHACL rule model (36 shapes/122 constraints) for HVAC compliance checking, including cardinality constraints, SPARQL-derived-value constraints, and even an active SHACL inference rule that *generates corrective data* (Listing 4, automatically resizing an undersized pipe). This is the single strongest empirical SHACL-implementation precedent in the whole corpus and directly narrows any claim that "quantified, real-building SHACL validation" alone is novel. The paper's own explicitly stated limitations (Sec. 6.2) are directly relevant to Paper 2's positioning: (1) "Limitations in manual corrections due to varying expertise" -- HVAC engineers lack SHACL skills, requiring interdisciplinary collaboration; (2) "Logical complexity" -- SHACL inference rules can only *add* knowledge, not delete stale data, requiring a separate SPARQL deletion step, increasing system complexity; (3) "Query efficiency" -- `FILTER NOT EXISTS` patterns caused the 87-second capacity-calculation slowdown; (4) "Geometry-based constraints" (e.g. separation/service distances between HVAC and structural components) were explicitly out of scope and named as future work. REMAINING_GAP for Paper 2: this paper validates structural/value completeness of a single-domain model at one point in time; it does not address GUID-anchored identity persistence, cross-system record accountability, or human-actor provenance -- all of which remain open even against this strongest available SHACL precedent.
