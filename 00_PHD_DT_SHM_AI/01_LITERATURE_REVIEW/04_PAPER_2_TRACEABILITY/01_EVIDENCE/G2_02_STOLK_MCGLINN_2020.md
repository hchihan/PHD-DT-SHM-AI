# G2_02 -- Stolk & McGlinn (2020)

**Validation of IfcOWL datasets using SHACL.** Proceedings of the 8th Linked Data in Architecture and Construction Workshop (LDAC 2020). Zotero key: 8HJN7D7E.

**Source read:** Full text, complete (`G2_8HJN7D7E_StolkMcGlinn.txt`, 14 pages).

---

**Q1 -- Research problem.** ifcOWL data-validation constraints are currently expressed using OWL restriction terminology, which OWL was never designed for (OWL restrictions are inference axioms under the Open World Assumption, not data constraints) -- risking incorrect interpretation and preventing reliable pre-import validation of ifcOWL models before conversion back to STEP for CAD tool import. The paper proposes migrating ifcOWL's data-validation constraints to SHACL (a Closed-World-Assumption, purpose-built RDF data-validation language) and demonstrates this on ifcOWL generated from geospatial data via R2RML.

**Q2 -- Information architecture.** PARTIAL/methodological, not a full sensor-to-record chain. CLAIM: chain is STEP/EXPRESS IFC schema -> ifcOWL (EXPRESS-to-OWL conversion) -> SHACL shapes (derived from ifcOWL's OWL restrictions via two methods: (1) SPARQL+SHACL-Advanced-Features rule-based extraction, (2) direct SHACLWriter.java generation alongside the existing OWLWriter.java in the EXPRESStoOWL tool) -> SHACL validation engine -> RDF validation report (conforms: true/false, itemized violations). Applied specifically to ifcOWL generated from R2RML-converted Ordnance Survey Ireland geospatial data (Prime2 dataset, 200,000+ buildings). No sensor/inspection/human-record layer is in scope.

**Q3 -- Identity representation.** YES, directly evidenced. CLAIM: `IfcGloballyUniqueId` values appear as SHACL `sh:focusNode` identifiers in the validation-report example (Listing 1.2), e.g. `data:IfcGloballyUniqueId_361c76fd-cdd3-4c56-aae1-848f3baecf77IfcOwnerHistory`. This is the paper's concrete mechanism for identifying *which* instance a validation violation applies to.

**Q4 -- Identity persistence across model revisions.** NOT_REPORTED. The paper validates a single generated ifcOWL model (from one R2RML conversion run); no discussion of GUID stability across successive conversions or model revisions.

**Q5a-d -- Four provenance types.** NOT_REPORTED. The paper's scope is schema/constraint validation (data types, cardinalities, class membership), not provenance of source/measurement/processing/human-actor. Note: the validation-report example itself catches an `IfcOwnerHistory`-typing violation (`ownerHistory_IfcRoot` must be typed as `ifc:IfcOwnerHistory`) -- `IfcOwnerHistory` is IFC's own built-in owner/history metadata class, but the paper treats it only as a schema-conformance target, not as an accountability mechanism it discusses or extends.

**Q5e -- Review/approval provenance.** NOT_REPORTED.

**Q6 -- Model/version context.** NOT_REPORTED.

**Q7 -- Validity/applicability scope.** YES, explicit. Method demonstrated specifically on ifcOWL version IFC2X3 TC1, generated from geospatial (2D building-footprint) data via R2RML; explicitly stated as reusable "by anyone generating ifcOWL models."

**Q8 -- Forward and reverse traceability.** PARTIAL. The `sh:focusNode` / `sh:resultPath` / `sh:value` triple in each validation result allows tracing a specific violation back to the exact RDF resource and property that caused it (a form of reverse traceability from error to source data), but no BIM-component-to-external-record traceability is addressed.

**Q9 -- Validation method.** YES -- this is the paper's entire contribution. SHACL shapes were derived from ifcOWL's existing OWL restrictions (two extraction methods compared) and applied to a real generated ifcOWL model (from R2RML-converted Irish Ordnance Survey geospatial data), producing an RDF SHACL validation report identifying specific violations, which was then used iteratively to fine-tune the R2RML transformation.

**Q10 -- Deliberate invalid-case testing.** YES, directly evidenced with concrete examples. CLAIM: the sample validation report (Listing 1.2) shows two real detected violations: (1) a `changeAction` property on `IfcOwnerHistory` with a malformed enumeration value ("Value must be an instance of ifc:IfcChangeActionEnum" -- caused by missing forward slashes in a URI value), and (2) an `ownerHistory_IfcRoot` property value that was not correctly typed as `IfcOwnerHistory` ("Value must be an instance of ifc:IfcOwnerHistory"). EVIDENCE: both are quoted directly from the RDF validation-report snippet with exact `sh:resultMessage` text and `sh:focusNode` GUIDs. LIMITATION: these are schema/type-conformance violations (malformed enum value, incorrect class typing), not the specific G1/G2 identity-integrity negative-case taxonomy in Paper 2's Q10 (orphan reference, duplicate GUID, stale GUID, wrong model revision, mismatched component, broken URI *between systems*, missing cross-system target, conflicting binding). IMPLICATION: this paper demonstrates real, working SHACL-based schema-validity negative-case detection *within* a single ifcOWL model, directly relevant to GAP-G/GAP-H, but does not test *cross-system referential integrity* (e.g., broken links between a BIM GUID and an external Condition_Evidence_ID or Inspection_Record_ID) -- which is closer to Paper 2's specific traceability-chain validation target.

**Q11 -- G3 record fields.** NOT_APPLICABLE -- this is a schema-validation paper, not an inspection-record paper. `IfcOwnerHistory` is referenced only as an IFC built-in class being validated for correct typing, not analyzed as an accountability mechanism (it natively lacks reviewer/approver semantics; it typically records only creating/last-modifying application and person, per the IFC standard, though the paper does not discuss this).

**Q12 -- ALREADY_ESTABLISHED vs REMAINING_GAP.** ALREADY_ESTABLISHED: SHACL-based schema/type-conformance validation of ifcOWL models, including concrete detection of malformed enumeration values and incorrect class-typing, with a demonstrated, reusable, tool-supported methodology (two extraction methods compared) and real-data validation (R2RML-converted geospatial-to-ifcOWL conversion). This directly narrows any claim that "SHACL-based validation of ifcOWL/IFC data is itself novel." REMAINING_GAP: the validation demonstrated is intra-model schema conformance, not cross-system referential-integrity validation of the specific Sensor_ID -> BIM_GUID -> Condition_Evidence_ID -> Inspection_Record_ID chain Paper 2 proposes; no persistence-across-revision, provenance, or record-accountability testing is present. Paper 2's contribution should be framed as extending SHACL-style validation from single-model schema conformance to cross-system, cross-record traceability-chain integrity.
