# G1_01 -- Fang, Teng, Shen, Yang & Lin (2025)

**Standardizing Design-Stage Digital-Twin Assets in a Smart Home for Building Data Management: Workflow Design and Validation Based on IfcGUID Compliance.** Buildings, 15(22), 4096. DOI: 10.3390/buildings15224096. Zotero key: YKGTBESL.

**Q1 -- Research problem.** How to govern the creation of design-stage digital-twin assets (delivered via a game-engine pipeline for a smart-home context) so that they remain compliant with IfcGUID identity rules, given that ad-hoc game-engine asset workflows risk breaking or duplicating GUIDs when converting/importing BIM geometry.

**Q2 -- Information architecture (Source -> mechanism -> BIM/component -> record -> output chain).** PARTIAL. The paper defines a workflow governance layer that sits between BIM authoring output and game-engine digital-twin assets, with IfcGUID compliance checks gating the conversion step. It does not define a full sensor -> evidence -> record chain; its chain is BIM model -> conversion/standardization workflow -> validated game-engine DT asset.

**Q3 -- Identity representation.** YES. Uses IfcGUID (the standard IFC GlobalId) as the identity anchor, explicitly testing whether GUIDs survive the BIM-to-game-engine asset pipeline.

**Q4 -- Identity persistence across model revisions.** PARTIAL. CLAIM: the workflow is validated for "IfcGUID compliance" during asset standardization. EVIDENCE: validation results reported in the paper's evaluation section. LIMITATION: the persistence tested is across a single conversion/standardization step (BIM -> DT asset), not across successive authoring-tool model revisions over the project lifecycle (design -> construction -> operation), which is the persistence question Paper 2's core chain depends on. IMPLICATION: this paper establishes that GUID-compliance validation techniques exist for at least one non-traditional pipeline stage, but does not close the cross-lifecycle-revision persistence gap.

**Q5a-d -- Four provenance types (source / measurement / processing / human-actor).** NOT_REPORTED for all four. The paper's focus is workflow/pipeline compliance, not provenance recording of data sources, measurements, or human actors.

**Q5e -- Review/approval provenance.** NOT_REPORTED.

**Q6 -- Model/version context.** PARTIAL. The workflow implies a design-stage snapshot (single model version) rather than explicit multi-version context tracking.

**Q7 -- Validity/applicability scope.** PARTIAL. Explicitly scoped to smart-home, design-stage, game-engine-delivered digital-twin assets -- a narrow, stated application context.

**Q8 -- Forward and reverse traceability.** NOT_REPORTED. No explicit discussion of tracing forward from BIM component to DT asset and back.

**Q9 -- Validation method.** YES. Workflow validated against IfcGUID compliance criteria as part of a design-stage case demonstration (details of pass/fail criteria in Results section, not fully re-extracted here).

**Q10 -- Deliberate invalid-case testing.** EVIDENCE_INSUFFICIENT. The extracted portion (through page ~28) did not surface an explicit missing-ID / orphan / duplicate-GUID / wrong-GUID / stale-GUID / wrong-model-revision / mismatched-component / broken-URI / missing-target / conflicting-binding / inconsistent-relationship test matrix. Given the paper's central IfcGUID-compliance framing, some such testing plausibly occurs in the Results section, but it was not confirmed in the read portion.

**Q11 -- G3 record-accountability fields (performer/reviewer/approver/timestamp/status/superseded-record/evidence-source).** NOT_APPLICABLE -- this is a G1 identity-focused paper, not an inspection-record paper.

**Q12 -- ALREADY_ESTABLISHED vs REMAINING_GAP.** ALREADY_ESTABLISHED (partial): GUID-compliance checking as a gate in a non-standard authoring/delivery pipeline is a demonstrated, real technique. REMAINING_GAP: this paper does not demonstrate identity persistence *across successive lifecycle-phase model revisions* (design->construction->operation) with different authoring tools and different files, which is the specific persistence claim in Paper 2's core chain -- so it narrows but does not close that gap.
