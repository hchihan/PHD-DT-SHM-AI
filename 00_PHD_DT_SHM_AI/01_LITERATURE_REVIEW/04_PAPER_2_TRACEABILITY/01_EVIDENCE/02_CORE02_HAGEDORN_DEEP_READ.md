# CORE-02 Deep Read

# Bibliographic identity

Hagedorn, P., Liu, L., König, M., Hajdin, R., Blumenfeld, T., Stöckner, M., Billmaier, M., Grossauer, K., & Gavin, K. (2023). BIM-Enabled Infrastructure Asset Management Using Information Containers and Semantic Web. *Journal of Computing in Civil Engineering*, 37(1), 04022041. DOI: 10.1061/(ASCE)CP.1943-5487.0001051. Zotero item key `4RKYF9RY`. No conflict between Zotero metadata and PDF.

# Research problem

Management/information-integration problem for **transportation infrastructure asset management (AM)**: existing Asset Management Systems (AMS) hold inspection/maintenance data in relational databases disconnected from BIM models; there is no standardized way to describe, update, and process asset-lifecycle data across BIM and existing AMS. Four explicit research questions (p. 04022041-2) drive a **web-based platform** implementing **ICDD (ISO 21597) information containers** to link BIM/IFC models with existing relational AMS databases.

# Information architecture

`IFC model → IFCtoLBD converter (RDF) + existing relational AMS database → R2RML mapping (relational DB → RDF) → ICDD information container (Ontology resources / Payload documents / Payload triples folders) → domain ontologies (BOT, BROT, EUROTL, PROV, ASBING) → SPARQL/SHACL queries on the container via a 5-layer web platform (data / data-access / service / business-logic / presentation)`

Stakeholder workflow layer: manager → engineer → contractor, mediated by Requirement/Delivery/Asset information containers with ISO 19650 status codes (work-in-progress / shared / published / archived) and PAS 1192-2 suitability labels.

# Identity mechanism

Component identity is **URI-based**, generated by the IFCtoLBD converter as BOT/BROT instance URIs (e.g. `elements:abutmentEast`, `elements:mainBeamSouth`, Fig. 12, p. 04022041-12). These instance URIs are then the anchor for linkset files (`Ls_ifc_element.rdf`, `Ls_element_inspection.rdf`) connecting them to condition-assessment and inspection-activity instances. **The paper does not discuss the raw IFC GlobalId as a separate, explicitly retained property** anywhere in the excerpts read (unlike CORE-01 and CORE-05); identity governance beyond "the converter assigns a URI" is NOT REPORTED. No discussion of GUID persistence, duplicate handling, or verifying converter output against the authoring-tool source.

# Linkage coverage

- **A. sensor/monitoring → BIM component:** NOT REPORTED as continuous sensor data; Use Case 2 links a *relational database of periodically measured pavement condition indicators* (friction, evenness, rut depth, crack width) to road-section IFC elements via R2RML + linksets — this is measurement-to-component linkage, but batch/periodic database records, not live sensor telemetry. PARTIAL.
- **B. BIM component → inspection record:** YES. Use Case 1: visual bridge inspection instances (ASBING condition grades for traffic safety/stability/durability, 0–4 scale) are created as EUROTL-typed instances and linked to BOT/BROT bridge-element instances via a linkset; the inspection activity itself (`inspections:Inspection2020`) is explicitly modeled with **PROV** properties `prov:wasAssociatedWith` linking it to an organization/actor (`inspections:EngineerOfficBridge`) and class `prov:Activity` (Fig. 12, p. 04022041-12). This is a genuine, well-modeled component→inspection-record linkage with actor provenance.
- **C. BIM component → maintenance/action record:** PARTIAL. Use Case 2 produces a "maintenance plan" (`Maintenance.instances.ttl`) linked to road sections via a linkset (`Ls_ifc_maintenance.rdf`), including recommended work/year/cost — but this is a **planned** maintenance program generated by a query filter, not a record of an executed action with a status/closure. Use Case 1 identifies which elements need maintenance (Stability grade 3) but does not carry that through to a formal maintenance-record entity.
- **D. technical evidence → inspection/action:** PARTIAL. Condition grade (evidence) → maintenance-need flag (Grade 3 "needs maintenance shortly", p. 04022041-12) is shown, but nothing beyond flagging — no closed-loop record of the action taken or its outcome.

# Provenance

PARTIAL/YES for actor+activity provenance specifically: the paper explicitly reuses the **W3C PROV** family (`prov:Activity`, `prov:wasAssociatedWith`, `prov:Organization`; and, in the pavement use case, `prov:generatedAtTime`, `prov:value`, `prov:atLocation` on `eurotl:Condition` instances, Fig. 9, p. 04022041-11) — this is the most standards-grounded provenance modeling among the 5 papers. **However:** no discussion of algorithm/tool-version provenance for how a condition grade was derived, and no review/approval-history trail beyond the container-level status codes (below).

# Model/version context

**YES — the strongest precedent among the 5 papers, but at the whole-container level, not per-component.** The ICDD platform implements ISO 19650-1 status codes (work in progress / shared / published / archived) plus a revision number and an explicit **"previous version" predicate** from ISO 21597-1 linking successive container versions (p. 04022041-6, "System Architecture of the ICDD Platform"). Archived containers preserve a change journal and cannot be edited; a new "work in progress" version is created for further changes. This is real, standards-based version continuity — but it versions the whole information container/exchange package, not an individual BIM_GUID's binding state across model revisions.

# Validity scope

NOT REPORTED. No applicability/context concept is modeled for when a condition-assessment or maintenance-plan record may be (re)used; PAS 1192-2 "suitability" labels (coordination, construction approval, AM inspection, AM maintenance, etc.) describe *what stage of process the container is fit for*, which is adjacent but not the same as Paper 2's evidence-applicability concept.

# Traceability level

**LEVEL 1–2 (one-way linkage, weak bidirectional).** Both use cases demonstrate forward retrieval (component → linked condition/maintenance data, e.g. Fig. 16's SPARQL query filtering pavement sections by crack width > 3 mm) and the container-status workflow gate ("fulfils requirement? yes/no", Fig. 2 and Fig. 4 BPMN diagrams) is a process-level check, not a data-traceability test. No reverse query is demonstrated (e.g. "given this maintenance plan entry, recover the original condition record and its actor"), and no explicit inverse-relationship consistency test (unlike CORE-01's Query 05) is reported.

# Validation design

**Two illustrative use-case demonstrations** (visual bridge inspection; pavement maintenance plan) on realistic but example data, each producing SPARQL query screenshots (Figs. 11, 13, 16) and container-content walkthroughs (Figs. 5, 6, 10). This is closer to "the system works and produces plausible output" than to a competency-question-driven correctness test: there are **no explicit competency questions listed up front**, no pre-registered expected answers, and no reported pass/fail count. This is a real methodological contrast with CORE-01 and especially CORE-05, and is important for Q8's warning: "system works" ≠ "relationship is verified".

# Invalid/negative tests

NOT REPORTED. No deliberate orphan/duplicate/wrong-version/broken-link case is constructed or tested anywhere in the two use cases. The "fulfils requirement? No → request improvement" branch in the BPMN process (Fig. 4) is a workflow approval gate on a human-authored deliverable, not a data-integrity test.

# Already established by this paper

- A real, ISO-19650/ISO-21597-grounded **container-version continuity mechanism** (status codes + previous-version predicate) — Paper 2 cannot claim "no prior work models version/revision continuity of an information package" as a gap; it can only claim that *per-component GUID-level* binding-across-revisions verification (rather than whole-container versioning) remains open.
- Genuine use of the **W3C PROV ontology** for actor/activity provenance on an inspection instance — a direct precedent for Paper 2's provenance requirements at the *actor* level (who performed/was associated with an inspection), though not at the *derivation/algorithm* level.
- A concrete BIM-component → condition-record → maintenance-plan linkage chain (Use Cases 1 and 2) demonstrated with real IFC models and a real relational AMS database via R2RML — a direct precedent Paper 2 must cite for "linking condition assessment records to BIM elements and to a maintenance plan" and must differentiate from by identity verification and accountable, closed-loop action status.

# Remaining gap relative to Paper 2

- No per-component/per-GUID identity verification or duplicate/versioning-across-revision handling (only whole-container versioning).
- Maintenance/action linkage stops at "planned work item," never reaches an executed, status-tracked, closable Action_Status.
- No validity-scope/applicability concept for reusing a condition or inspection record.
- No competency-question-driven, pre-registered-expected-answer validation protocol; no reported denominators.
- No deliberate identity/link-integrity negative tests of any kind.
- No bidirectional (reverse) query demonstrated; traceability shown is forward/one-way only.

# Claim → Evidence → Limitation → Implication

**Claim:** ICDD-based information containers, populated via IFCtoLBD and R2RML and annotated with PROV, EUROTL, and ASBING ontologies, can link BIM models to existing AMS databases for inspection and maintenance planning.
**Evidence:** §"Use Cases" (pp. 04022041-8 to 04022041-11), Figs. 4–16, showing container structure, linksets, and two SPARQL queries with results.
**Limitation:** Validation is two illustrative use cases with SPARQL-query screenshots; no competency questions, no pre-registered expected answers, no negative/invalid-link tests, no per-component identity verification. Explicitly stated as future work: "the connection to sensors and other measuring devices that produce regular time-dependent data must be made usable in information containers automatically" (p. 04022041-14 Conclusion) — i.e. the authors themselves flag that live sensor→BIM integration is *not yet done* here.
**Implication for Paper 2:** Paper 2 can cite CORE-02 as the strongest existing precedent for (a) actor-provenance via PROV and (b) container-level version continuity, and must explicitly differentiate its contribution as *component-level* (GUID-bound, verified-against-actual-export) identity governance plus a closed, accountable Action_Status — neither of which CORE-02 provides. Paper 2 also cannot claim to be first to reuse PROV in this domain.
