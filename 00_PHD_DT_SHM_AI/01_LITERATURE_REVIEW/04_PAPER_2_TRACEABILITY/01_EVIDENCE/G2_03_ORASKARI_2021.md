# G2_03 -- Oraskari, Senthilvel & Beetz (2021)

**SHACL is for LBD what mvdXML is for IFC.** Proceedings of the 38th CIB W78 Conference. Zotero key: AQDJR2UE.

**Source read:** Full text, complete (`G2_AQDJR2UE_OraskariEtAl.txt`, 10 pages).

---

**Q1 -- Research problem.** Within an EU-funded building-renovation project (BIM4Ren), tool workflows require Linked Building Data (LBD, converted from IFC via BOT-based converters) that fulfil application-specific exchange requirements. The paper investigates (1) how to unit-test IFC-to-LBD converters to catch data loss/corruption/errors during conversion, and (2) how SHACL can play the role for LBD that mvdXML (Model View Definitions) plays for IFC, i.e. define and validate application-specific data views/exchange requirements.

**Q2 -- Information architecture.** PARTIAL/methodological. Chain is: IFC STEP model -> IFC-to-LBD converter (e.g. IFCtoLBD, Revit BOT-exporter plugin) -> BOT-aligned RDF/LBD graph -> SHACL-SPARQL constraint rules -> (a) unit-test pass/fail report on conversion correctness, or (b) filtered MVD-equivalent subgraph for a specific exchange scenario (e.g. energy simulation). No sensor/inspection-record layer; focused entirely on conversion-quality assurance and model-view definition.

**Q3 -- Identity representation.** YES, and this is the paper's central mechanism for cross-model matching. CLAIM: "In the IFC context, [ontology-mapping individual correspondence] can be solved by comparing IFC GUIDs. Therefore the problem can be expressed: For all instances with an alignment and a GUID attribute, there has to be exactly one instance counterpart with the same GUID in the LBD graph." EVIDENCE: Listing 1 (Requirement R1 SHACL rule) explicitly uses `ifc:globalId_IfcRoot/express:hasString` and a `FILTER NOT EXISTS` SPARQL pattern to check that every GUID present in the source ifcOWL graph has a matching counterpart in the target BOT/LBD graph.

**Q4 -- Identity persistence across model revisions.** PARTIAL. CLAIM: the paper tests GUID-based individual-correspondence persistence *across a format conversion* (IFC->LBD), not across successive authored project-phase model revisions. EVIDENCE: Requirement R1's unit test (Listing 1) and the auto-generated cross-converter comparison (Listing 4, comparing IFCtoLBD output against an independent Revit-plugin LBD export of the *same* underlying IFC model) both hold the underlying IFC model fixed and test whether GUIDs survive *format transformation*, not model revision. LIMITATION: this is conversion-fidelity testing, not lifecycle-revision persistence testing. IMPLICATION: directly informs, but does not close, Paper 2's identity-persistence-across-revision claim -- it establishes that GUID-based cross-representation matching via `FILTER NOT EXISTS` SPARQL patterns is a working, precedented technique, transferable in principle to a revision-comparison use case.

**Q5a-d -- Four provenance types.** NOT_REPORTED. No source/measurement/processing/human-actor provenance discussion; scope is purely conversion-quality and MVD-filtering validation.

**Q5e -- Review/approval provenance.** NOT_REPORTED.

**Q6 -- Model/version context.** NOT_REPORTED explicitly as a "version" concept, though the cross-converter comparison (Sec. 3.2, using the "BOT Duplex Apartment" test file exported independently by two different converters from the same IFC model) is architecturally close to a two-version-comparison scenario.

**Q7 -- Validity/applicability scope.** YES. Scoped explicitly to two BIM4Ren-project use cases: (1) IFC-to-LBD converter unit testing (tested against IFCtoLBD and an independent Revit BOT-exporter plugin, both applied to the same BOT Duplex Apartment IFC model), and (2) an Energy Simulation MVD use case (filtering windows with associated 3D geometry and specific size properties for energy-performance exchange).

**Q8 -- Forward and reverse traceability.** PARTIAL. GUID-based `FILTER NOT EXISTS` checks (Listings 1-2) provide reverse traceability from a source IFC individual to its LBD counterpart (or flag its absence); checksum-based drift detection (Listing 3, MD5 hash of an ordered triple set for a specific element, e.g. `inst:stairflight_ca457005-...`) provides a form of forward change-detection for a *specific, named* element instance across converter runs.

**Q9 -- Validation method.** YES, multiple concrete methods demonstrated and tested with real tooling (TopBraid SHACL API) on real data (BOT Duplex Apartment IFC model, converted via two independent tools): (1) GUID-based alignment-existence unit tests (Requirement R1); (2) property/relationship-alignment existence tests (Requirement R2, e.g. checking `bot:hasBuilding` relation exists); (3) checksum-based per-element drift detection; (4) auto-generated SHACL rules comparing two independent converters' outputs at the topological level; (5) SHACL SPARQL Construct-based MVD-equivalent filtering for the energy-simulation use case.

**Q10 -- Deliberate invalid-case testing.** YES, directly and explicitly. CLAIM: the paper's entire "Requirement R1"/"Requirement R2" unit-test framework is designed specifically to catch *missing counterparts* -- i.e., orphaned/unmatched instances and missing relationships -- using `FILTER NOT EXISTS` SPARQL patterns embedded in SHACL constraints. EVIDENCE: Listing 1's `sh:message "GUIDs of the alignment instances should match."` fires precisely when a GUID exists in the source but has no `props:globalIdIfcRoot_attribute_simple` counterpart in the target graph -- this is a direct, working implementation of "missing target"/"broken cross-system reference" detection in Paper 2's Q10 taxonomy. Listing 2 similarly detects a *missing relationship* (`bot:hasBuilding missing`) between two otherwise-matched GUID-identified individuals -- directly matching Paper 2's "inconsistent relationship" negative-case category. Listing 3's checksum test detects unexpected property-level drift for a named element -- directly matching a "stale/changed record" detection pattern. LIMITATION: these tests were run against controlled converter-output pairs from the same source model, not against independently authored, temporally separated model revisions or against a genuinely cross-system chain spanning sensor/inspection records. IMPLICATION: **this is the strongest direct precedent found in the entire targeted corpus for negative/invalid-case SHACL testing of GUID-based cross-representation integrity** (missing-counterpart and missing-relationship detection specifically), materially narrowing any claim that such negative testing is itself novel to Paper 2. Paper 2's contribution must be differentiated by extending this pattern from single-conversion-pair testing to a full multi-hop, cross-system, human-accountable traceability chain.

**Q11 -- G3 record fields.** NOT_APPLICABLE -- no inspection-record content; entirely a data-conversion/model-view validation paper.

**Q12 -- ALREADY_ESTABLISHED vs REMAINING_GAP.** ALREADY_ESTABLISHED: GUID-based `FILTER NOT EXISTS` SHACL-SPARQL patterns for detecting missing/orphaned cross-representation counterparts and missing relationships, plus checksum-based per-element drift detection -- concrete, tested, GitHub-published methods. REMAINING_GAP: (1) tested only across format-conversion pairs of the *same* underlying IFC model, not across genuinely independent lifecycle-phase model revisions or cross-system record chains (Sensor_ID/Condition_Evidence_ID/Inspection_Record_ID); (2) no human-actor/reviewer/approver accountability layer; (3) the paper itself notes (Sec. 4) that "SHACL is designed to focus on finding rule violation errors... which causes it to accept inputs where SHACL rule targets are missing" -- i.e., SHACL's default behavior under-detects missing nodes unless unit tests explicitly check node existence separately, a subtle validation-design limitation directly relevant to how Paper 2 should design its own negative-case test suite.
