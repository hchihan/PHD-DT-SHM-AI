# G2_05 -- Beach, Rezgui, Li & Kasim (2015)

**A rule-based semantic approach for automated regulatory compliance in the construction sector.** Expert Systems with Applications, 42, 5219-5231. DOI: 10.1016/j.eswa.2015.02.029. Zotero key: XWZYTUV6.

**Source read:** Full text, complete (`G2_XWZYTUV6_BeachEtAl.txt`, 29 pages).

---

**Q1 -- Research problem.** Converting complex, human-readable regulatory text (e.g. building codes, sustainability rating schemes) into computer-executable compliance-checking rules is costly and typically requires close, expensive collaboration between domain experts and software developers, producing closed systems only vendors can update. The paper proposes a methodology allowing domain experts (not software developers) to specify and maintain regulatory-compliance rules directly, based on three decoupled semantic domains: the target domain, the regulation-specific view of that domain, and the data-file-format semantics (in this case, IFC).

**Q2 -- Information architecture.** YES -- a full, real, end-to-end architecture is defined and demonstrated. CLAIM: chain is regulatory document (RASE-tagged: Application/Selection/Exception/Requirement) -> Regulation Ontology (built via metadata tagging of the regulation text) -> Regulation Mapping Ontology (class- and property-level mappings from regulation-ontology classes to Data Format Ontology classes, e.g. `Contractor` class mapped to `IfcActor` restricted to instances with a property set to "Contractor") -> SWRL rule engine execution against a semantic-translator-converted A-Box (from an uploaded IFC data file) -> Results (RegulationApplicable/RegulationFailed/RegulationPassed individuals) -> credit-score calculation algorithm -> user interface. EVIDENCE: Figures 1-2, 6-11, and Listings of generated SWRL rules for BREEAM MAN2 credits. LIMITATION: the chain ends at a compliance score/pass-fail result, not at a human-accountable inspection record.

**Q3 -- Identity representation.** NOT_REPORTED at the GUID level specifically; entities are matched by IFC class and property-value restriction (e.g. `IfcActor` instances where a property equals "Contractor"), not by `IfcRoot.GlobalId` persistence.

**Q4 -- Identity persistence across model revisions.** PARTIAL/NOT_REPORTED. CLAIM: the case study explicitly describes an iterative "shadowing" validation process run in tandem with real building design over time (BREEAM/Building Regulations checks performed as the London office building's IFC model evolved through design), implying the system was re-run against successive model states, but no explicit discussion of how GUID or entity identity was tracked/matched across those successive IFC file versions was found in the extracted text. IMPLICATION: this is a real multi-revision-adjacent use case but the paper does not surface an explicit identity-persistence mechanism, leaving this a genuine gap rather than a confirmed established technique.

**Q5a-d -- Four provenance types.** NOT_REPORTED. No sensor/measurement/processing provenance concept; regulation-checking is against static building-model data.

**Q5e -- Review/approval provenance.** NOT_REPORTED. The system architecture allows a user to "supply required additional data" when information is missing (Figure 2, step 4), and the paper notes that user-supplied data is treated as "less authoritative" than data calculated/extracted directly from the data file -- a rudimentary trust/provenance distinction -- but no explicit reviewer/approver role, timestamped record, or superseded-record concept is defined.

**Q6 -- Model/version context.** NOT_REPORTED explicitly, though the "shadowing" validation process (Sec. 4.3) implies repeated runs against an evolving model.

**Q7 -- Validity/applicability scope.** YES, explicit and substantial. CLAIM: methodology validated over an 18-month full-scale case study with industrial partners (BRE, LABC, Skanska UK, AEC3), automating the Code for Sustainable Homes (229 data items, 64 procedures), BREEAM (854 data items, 180 procedures), and UK Building Regulations (239 data items, 166 procedures), applied to a real nine-floor, 85,000 sq ft office building in London designed to achieve BREEAM Excellent, with a Bentley Microstation plug-in interface.

**Q8 -- Forward and reverse traceability.** YES, explicitly claimed as a system requirement and demonstrated. CLAIM: the methodology "maintains strong links between the extracted regulations and the original text from which they have been generated" and the interface (Figure 13) "shows how rules are presented to the users in a way that related them back to the text in the regulation documents," including which specific data object caused a regulation to fail (a `hasFailedRegulation` property is asserted on the failing object, per the SWRL rule listing).

**Q9 -- Validation method.** YES -- ground-truth comparison against manual assessment. CLAIM: the full BREEAM and UK Building Regulations checks were run "in tandem" with the standard manual assessment process used by the construction industry, and results compared; a worked example (BREEAM Pollution Issue 01) is reported with matching manual-vs-automatic results across four credit-scoring rules (Table 2), all marked with the correct pass/fail symbol in both columns.

**Q10 -- Deliberate invalid-case testing.** PARTIAL. CLAIM: the system explicitly handles the case of missing/incomplete data using the Open World Assumption: "a rule is deemed to not be within scope unless it can be determined that it is in scope... to enable the system to handle situations where information may be missing from data files and enable us to give us the valid outcome of 'unknown'." EVIDENCE: explicit design rationale in Sec. 3.3.1, and the interface (Figure 13) shows question-mark circles for "unknown data." LIMITATION: this is missing-data/incompleteness handling (returning "unknown" rather than false-failing), not the specific identity-integrity taxonomy of Paper 2's Q10 (duplicate/orphan/stale GUID, broken cross-system reference). IMPLICATION: shows a real, deployed precedent for principled "not enough information" handling (as opposed to silently inferring NO), directly relevant methodologically to Paper 2's own evidence-labeling discipline (YES/PARTIAL/NO/NOT_REPORTED/EVIDENCE_INSUFFICIENT), though applied to regulatory-rule scope rather than record-identity integrity.

**Q11 -- G3 record fields.** NO for performer/reviewer/approver/status/superseded-record; the only "provenance-adjacent" distinction found is the authoritative-vs-user-supplied data split noted under Q5e.

**Q12 -- ALREADY_ESTABLISHED vs REMAINING_GAP.** ALREADY_ESTABLISHED: a real, 18-month, multi-organization, three-semantic-domain (regulation/domain/data-format) rule-based compliance-checking methodology validated against manual ground truth on a real building, with strong forward traceability from rule result back to source regulation text and to the specific failing BIM object, and principled open-world handling of missing information. This is a mature, older (2015) precedent for "rule-based semantic compliance validated against manual assessment," which Paper 2 should cite as established territory for validation-methodology design, though it predates and does not use SHACL. REMAINING_GAP: no GUID-based identity mechanism or persistence-across-revision discussion, no reviewer/approver/record-accountability layer, and no deliberate identity-integrity negative-case testing (only missing-data/incompleteness handling) -- all still open for Paper 2.
